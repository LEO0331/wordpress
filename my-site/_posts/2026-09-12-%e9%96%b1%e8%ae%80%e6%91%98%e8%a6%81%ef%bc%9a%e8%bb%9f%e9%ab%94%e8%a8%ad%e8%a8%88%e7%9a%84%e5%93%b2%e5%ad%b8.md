<p class="wp-block-paragraph">簡介：軟體設計最大的敵人就是複雜性。本書不是在教某一套框架，也不是在講某個語言的最佳實踐，為什麼有些程式一開始看起來可以跑，但過幾個月之後就變得很難改？為什麼有些功能只是小改，最後卻牽一髮動全身？為什麼工程師常常不是在寫新功能，而是在跟一堆看不懂、拆不開、改了會爆的 code 纏鬥？複雜性會讓系統難以建構、難以維護，甚至也可能讓系統變慢；而造成複雜性的來源，常常是依賴關係太多、資訊不清楚、抽象層混亂、錯誤條件過度暴露，或是命名太籠統。本書提出實用的觀念像是「模組應該要深」、「資訊隱藏」、「不同層要有不同抽象」、「設計它兩次」、「先寫註解」、「程式碼應該顯而易見」，都不是很炫的技巧，都很接近真實開發裡每天會遇到的問題。</p>



<p class="wp-block-paragraph">心得：會重新定義好程式碼。剛開始寫程式時，很容易把重點放在功能有沒有做出來、測試有沒有過、畫面有沒有長對，這些只是基本盤，真正麻煩的是，三個月後你回來改這段 code，還看不看得懂？下一個工程師接手時，會不會需要通靈？一個需求變更，會不會讓整個系統到處破？工作程式碼是不夠的：程式可以跑不代表設計是好的，技術債就是這樣來的，當下為了趕 deadline，覺得先塞一下、先 workaround、先複製一份，反正現在能動就好，這些小小的妥協累積起來就會變成系統的複雜性，到最後團隊不是在開發產品，而是在保護一個不能亂碰的怪物。</p>



<p class="wp-block-paragraph">深模組的概念：一個好的模組應該用簡單的 interface，包住比較多有價值的內部實作，外面的人不用知道裡面怎麼做，只要知道怎麼用就好。好的抽象會讓使用者覺得事情變簡單；爛的抽象則是看起來有分層，實際上每一層都把細節漏出來，最後大家還是要懂整坨系統。資訊隱藏：很多系統難維護，不是因為功能真的很難，而是因為資訊到處外洩，某個欄位的意義、某個狀態的判斷、某個流程的限制，被散落在不同檔案、不同函式、不同 if else 裡，結果需求一改，你根本不知道要改哪裡，也不知道有沒有漏改，這種 code 最可怕的地方不是醜，而是不可信任。</p>



<p class="wp-block-paragraph">作者不是鼓勵寫廢話註解，而是認為註解應該描述程式碼本身看不出來的東西，例如設計意圖、限制、為什麼這裡不能那樣做，因為 code 可以告訴你它做了什麼，但不一定能告訴你為什麼要這樣做。好的設計前期看起來會比較慢，因為要想抽象、切模組、寫清楚文件、避免把複雜性丟給未來，但長期來看，這些投資會回收，早期仔細定義的模組、清楚的文件，以及設計能力的累積，後面都會省下大量時間；一旦熟悉方法，好的設計其實不一定比草率設計花更多時間。</p>



<p class="wp-block-paragraph">本書沒有把軟體設計講成架構師才需要管的事，每一次命名、每一次拆函式、每一次設計 interface、每一次決定錯誤要不要往外拋，其實都在影響系統未來的可維護性。是一本讀完會改變看 code 的角度，會開始問：這個設計有沒有讓事情變簡單？這個 interface 有沒有洩漏太多細節？這個錯誤真的需要存在嗎？這個名字是不是太空泛？好的設計，是為了降低未來理解和修改的成本，比追求看起來很厲害的架構更重要，真正的好系統，不是第一天寫得很快，而是半年後、一年後，團隊還敢改、還能懂、還能穩定往前長。</p>



<ol class="wp-block-list">
<li>工作程式碼是不夠的，真正的挑戰是未來還改不改得動。</li>



<li>軟體設計最大的敵人，不是語法，而是複雜性。</li>



<li>好設計不是把東西拆很多層，而是讓每一層都有清楚的抽象。</li>



<li>模組應該要深，interface 要簡單，內部實作才值得複雜。</li>



<li>爛抽象最麻煩的地方，是看起來有分層，實際上細節到處外洩。</li>



<li>資訊隱藏不是把 code 藏起來，而是把變動控制在最小範圍。</li>



<li>如果一個小改動需要改很多地方，通常代表設計已經在提醒你出事了。</li>



<li>命名不是小事，模糊的名字會製造模糊的理解。</li>



<li>註解不該重複程式碼，而是補上程式碼看不出來的設計意圖。</li>



<li>好的 interface 會讓使用者不用知道太多內部細節。</li>



<li>複雜性最可怕的地方，是它通常不是一次爆炸，而是一點一點累積。</li>



<li>技術債不是抽象概念，它就是未來每一次修改時多付出的時間。</li>



<li>設計不是前期浪費時間，而是在替未來的維護成本先付款。</li>



<li>好設計會讓後來的人少猜一點、少怕一點、少踩雷一點。</li>



<li>不必要的錯誤狀態，本身就是一種複雜性。</li>



<li>寫 code 之前先想清楚 interface，通常比寫完再補救更有效。</li>



<li>好的程式碼應該顯而易見，不需要每次閱讀都像在解謎。</li>



<li>架構不是畫圖時才存在，而是每一個日常決策累積出來的結果。</li>



<li>能跑只是起點，能長期維護才是工程品質。</li>



<li>乾淨、簡單、明顯的設計，本身就是一種工程美感。</li>
</ol>



<p class="wp-block-paragraph">書名：A Philosophy of Software Design<br>作者：John Ousterhout <br>出版：Yaknyam Press</p>
